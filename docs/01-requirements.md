# 01 Requirements：CramPlan 期末考讀書排程

> Design Only｜對應 W03 Requirements Engineering

## 1. Problem Statement

期末考週通常有好幾科集中在一兩週內。學生每天都要重新判斷「今天該讀哪一科」，容易挑自己喜歡或比較熟的科目讀，等到某科考試前一天才發現幾乎沒準備；前幾天沒讀完的進度，也沒有地方提醒自己。

CramPlan 根據各科考試日期，每天只給一個明確答案：今天讀哪一科，並附上判斷依據（距離考試幾天、這科先前漏讀幾天）。

## 2. Users

| 角色 | 是否直接使用 | 主要需求 |
|---|---|---|
| 準備期末考的大學生 | 是 | 登錄考試、每天知道該讀哪一科、記錄完成情況 |

本版只有單一使用者，不設計登入與權限。

## 3. User Scenario

小明期末有三科考試：物理 2027-01-09、微積分 2027-01-11、英文 2027-01-13。

1. 2027-01-05，他依序登錄三科考試，按下「產生排程」。
2. 系統從 1/5 排到最後一科考試的前一天 1/12：1/5～1/8 讀物理、1/9～1/10 讀微積分、1/11～1/12 讀英文。每一天只有一科。
3. 1/5 他讀完物理，把當天任務標記為已完成。
4. 1/6 他有事沒讀，任務維持未完成。
5. 1/7 他打開系統，按下「重新排程」。系統保留 1/5 的完成紀錄與 1/6 的未完成紀錄，從 1/7 起重新排程，並在每筆物理任務上標示「物理先前漏讀 1 天」。
6. 小明看到提醒，知道物理要加把勁。

## 4. 亮點如何幫使用者完成任務

| 亮點 | 情境中的表現 | 支援的設計 |
|---|---|---|
| 每天只給一個答案 | 1/7 打開系統，只看到「今天讀物理」 | BR-05、BR-06；`GET /study-tasks?date=` |
| 附上判斷依據 | 任務顯示「距離物理考試 2 天」 | `StudyTask.days_until_exam`（計算欄位） |
| 漏讀提醒 | 重新排程後顯示「物理先前漏讀 1 天」 | BR-09；`StudyTask.missed_days`（計算欄位） |

## 5. Functional Requirements

| ID | 功能需求 | 來源 |
|---|---|---|
| FR-01 | 系統應允許使用者登錄一科考試，包含科目名稱與考試日期。 | Scenario 1 |
| FR-02 | 系統應允許使用者查看已登錄的考試，依考試日期由早到晚排列。 | Scenario 1 |
| FR-03 | 系統應依排程規則，產生從開始日期到最後一科考試前一天的讀書任務，每天一科。 | Scenario 2 |
| FR-04 | 系統應允許使用者查看指定日期的讀書任務，並顯示距離該科考試的天數。 | Scenario 2、5 |
| FR-05 | 系統應允許使用者把任務標記為已完成，或取消已完成。 | Scenario 3 |
| FR-06 | 系統應允許使用者重新產生排程，並在新任務上標示該科先前漏讀的天數。 | Scenario 5 |

## 6. Business Rules

### 考試資料

| ID | 規則 |
|---|---|
| BR-01 | 科目名稱不可空白，長度 1～30 字元。 |
| BR-02 | 登錄時，考試日期必須晚於當天。 |
| BR-03 | 尚未考完的考試中，科目名稱不可重複。 |

### 排程範圍與分配

| ID | 規則 |
|---|---|
| BR-04 | 排程範圍為「開始日期」到「最晚一科考試的前一天」。開始日期可由 Client 指定，未指定時為今天。開始日期之後若沒有任何考試，不產生排程。 |
| BR-05 | 排程範圍內每一天恰好安排一科。 |
| BR-06 | 每天安排「考試日期晚於當天、且最早考」的科目（最緊急）。若有多科同一天考試，先登錄的科目（id 較小）優先。 |

### 重新排程

| ID | 規則 |
|---|---|
| BR-07 | 產生排程時，刪除開始日期當天及之後所有「未完成」的任務，再依 BR-05、BR-06 重新安排。 |
| BR-08 | 已完成的任務一律保留；開始日期之後若某天已有已完成的任務，該天不再安排新任務。開始日期之前的未完成任務也保留，作為漏讀紀錄。 |
| BR-09 | 某科的「漏讀天數」= 該科日期早於今天、且狀態仍為未完成的任務數。 |

### 任務狀態

| ID | 規則 |
|---|---|
| BR-10 | 任務狀態只有 `PENDING`（未完成）與 `DONE`（已完成），兩者可以互相切換。 |

### 已知限制（我的決定：本版不處理）

依 BR-06，若兩科在同一天考試，後登錄的科目在考前不會被分到任何一天。例如微積分與英文都在 1/20 考，英文不會出現在排程中。此限制已在設計階段評估，決定本版不處理（見 `05-ai-collaboration.md` 第 3 輪）。

## 7. Non-functional Requirements

| ID | 非功能需求 | 類型 |
|---|---|---|
| NFR-01 | 相同的考試資料、任務狀態與開始日期，產生的排程必須完全相同。 | 一致性 |
| NFR-02 | 在 10 科以內、排程 60 天以內的情況下，產生排程應於 1 秒內完成。 | 效能 |
| NFR-03 | 錯誤回應須指出違反的欄位或規則，讓使用者不看程式碼就能修正。 | 可理解性 |

## 8. Scope

### In Scope

- 登錄與查看考試
- 依最緊急規則產生每天一科的排程
- 查看指定日期任務，含距離考試天數
- 標記完成或取消完成
- 重新排程並標示漏讀天數

### Out of Scope

| 項目 | 原因 |
|---|---|
| 依難度、每日可讀時數分配時間 | 我選擇最簡單的「最緊急」規則，維持小而美 |
| 同日考試的公平分配 | 已知限制，我決定本版不處理 |
| 修改、刪除考試 | 非核心流程；登錄錯誤可在下一版處理 |
| 登入、多使用者 | 課程作業建議避開登入權限 |
| 提醒推播、行事曆同步 | 依賴外部服務，超出範圍 |
| AI 判斷讀書內容 | 本系統只決定「讀哪一科」 |

## 9. Acceptance Criteria

以下例子共用資料：物理 2027-01-09（id 1）、微積分 2027-01-11（id 2）、英文 2027-01-13（id 3），皆於 2027-01-05 前登錄。

| ID | 對應 | 驗收條件 |
|---|---|---|
| AC-01-01 | FR-01 | 給定今天是 2027-01-05，當使用者登錄「物理、2027-01-09」時，系統應建立該考試並回傳其 id。 |
| AC-01-02 | FR-01、BR-02 | 給定今天是 2027-01-05，當使用者登錄考試日期為 2027-01-05 時，系統應拒絕並說明考試日期必須晚於今天。 |
| AC-01-03 | FR-01、BR-03 | 給定「物理」已登錄且尚未考完，當使用者再登錄一科「物理」時，系統應拒絕並說明科目重複。 |
| AC-02-01 | FR-02 | 當使用者查看考試清單時，應依序看到物理、微積分、英文。 |
| AC-03-01 | FR-03、BR-04～BR-06 | 給定開始日期 2027-01-05，產生排程後應有 8 筆任務：1/5～1/8 物理、1/9～1/10 微積分、1/11～1/12 英文，每天一筆。 |
| AC-03-02 | FR-03、BR-04 | 給定開始日期 2027-01-13，之後已沒有任何考試，系統應拒絕產生排程並說明原因。 |
| AC-04-01 | FR-04 | 給定上述排程，查詢 2027-01-07 的任務時，應回傳一筆物理任務，距離考試 2 天。 |
| AC-05-01 | FR-05、BR-10 | 當使用者把 1/5 的任務標記為 DONE，再查詢該任務時狀態應為 DONE；再改回 PENDING 也應成功。 |
| AC-06-01 | FR-06、BR-07～BR-09 | 給定 1/5 任務為 DONE、1/6 任務為 PENDING，今天為 2027-01-07，以開始日期 2027-01-07 重新排程後：1/5、1/6 的任務保留；1/7～1/8 為物理且漏讀天數為 1；1/9 之後的任務與原本相同，漏讀天數為 0。 |
| AC-06-02 | FR-06、BR-08 | 給定 1/8 的任務已提前標記為 DONE，以開始日期 2027-01-07 重新排程後，1/8 保留原本的已完成任務，不再新增任務。 |
